## Critical findings

### F01 [P1] act_and_observe authorizes one PID and executes another

**Evidence:** `src/Winsight.Mcp/Tools/AgentExperienceTool.cs:259`, `:275`; `src/Winsight.Core/Modules/Orchestration/StepRunner.cs:122`.

The macro validates `processId ?? step.ProcessId`, then passes the unchanged step to the runner. The runner selects `step.ProcessId ?? defaultProcessId`. Supplying an allowed outer PID A and a denied step PID B therefore validates A but executes on B. Before/after observations also describe A, concealing the actual target's changes. `run_steps` correctly rejects the same step through `ValidateBatchPolicy`.

**Reproduced:** restrict `WINSIGHT_ALLOWED_PROCESS_IDS` to the probe's own PID; put the separate sample PID only in `step.ProcessId`; request an IncrementButton click through `act_and_observe`. The macro returned success and the denied sample's CountLabel became `Count: 1`. No third-party application was used for this reproduction.

**Fix:** resolve one effective PID, authorize it, and use it consistently for the step and both observations; reject contradictory IDs or normalize the step before dispatch. Add an integration regression asserting both rejection and an unchanged denied target.

### F02 [P1] close_app(force=false) can discard unsaved work

**Evidence:** `src/Winsight.Core/Modules/Lifecycle/AppLauncher.cs:145-154`; default grace is 5000 ms at line 31.

After `CloseMainWindow`, the implementation kills the entire process tree if the application has not exited within five seconds. It also kills immediately when no close request can be sent. A save-confirmation dialog, a user declining close, or a slow graceful shutdown therefore results in forced termination despite `force=false`. The fallback is documented, so this is a dangerous default rather than an undocumented implementation discrepancy.

**Verification:** direct control-flow inspection; no unsaved user application was terminated. Microsoft documents that an application can ask for confirmation or refuse a `CloseMainWindow` request: [Process.CloseMainWindow](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.closemainwindow?view=net-10.0).

**Fix:** return a structured still-running/confirmation-required result after the grace period. Require an explicit force request for `Kill(entireProcessTree: true)`. Test with a fixture that cancels closing.

### F03 [P1] baseline replacement ignores global dry-run

**Evidence:** `src/Winsight.Mcp/Tools/CompareVisualBaselineTool.cs:100-112`; documented global policy in `README.md:337`.

`compare_visual_baseline` captures and calls `File.Copy(..., overwrite: true)` without consulting `ToolAccessPolicy.IsDryRunEnabled`. With `updateBaseline=true`, an approved reference is overwritten while global simulation is enabled. Baseline creation is likewise performed when the key is absent.

**Reproduced:** an audit-only baseline file changed SHA-256 under `WINSIGHT_DRY_RUN=true`; the response reported `verdict=baseline_updated` and `passed=true`.

**Fix:** guard baseline mutation before capture/pruning and return a preview when dry-run is enabled. Cover existing and missing baseline cases with byte-preservation tests. The issue is the violated simulation contract, not the explicitly requested update behavior in ordinary mode.

### F04 [P1] coordinate bounds do not establish the recipient of a physical click

**Evidence:** `src/Winsight.Core/Modules/UiAutomation/ActionInvoker.cs:100-146`; `WindowGeometry.cs:69` onward.

`ClickPoint` checks whether the coordinate lies in a rectangle belonging to the requested process, then calls the global mouse API. It neither brings that window to the foreground nor verifies the window actually occupying the screen point. If another application's window covers that rectangle, the check passes and physical input goes to the covering application. The process allowlist and `allowOutOfWindow=false` therefore do not contain this input to the authorized process.

**Verification:** complete call-path inspection; the covering-window scenario was not physically exercised against a user application. The ordinary foreground sample E2E does not test occlusion.

**Fix:** establish and verify the intended window, then check the actual window/process at the point immediately before input; refuse an occluded or changed target. Serialize desktop input operations to reduce interleaving. Add a two-fixture occlusion test that checks the excluded window receives no input.

## Important findings

### F05 [P2] tracing failures escape ToolSafety after the tool has executed

**Evidence:** `src/Winsight.Mcp/Tools/ToolSafety.cs:45-56`, `:72-81`, `:101-119`; `TraceRecorder.cs:41`, `:96`, `:124`.

The success path writes the trace inside the try block. If directory creation or append fails, the catch path writes the trace again without a guard. That second failure escapes the supposedly safe wrapper. For a mutating operation, the underlying action may already have succeeded while the caller receives an error and retries it.

**Reproduced:** point `WINSIGHT_TRACE_DIR` at an existing fixture file and call `get_target`. Result: `TRACE_ESCAPED=IOException`. This proves the boundary violation, not that the MCP SDK necessarily terminates the host; host termination was not demonstrated.

**Fix:** make recording independently best-effort and non-throwing, including error-path recording. Preserve the original operation result. Test directory, permission, and append failures for all three safety wrappers.

### F06 [P2] batch screenshots collide before execution

**Evidence:** `src/Winsight.Mcp/Tools/ScreenshotOutput.cs:31`, `:62-63`; `RunStepsTool.cs:109-121`.

Default paths contain only a prefix and a millisecond timestamp. `run_steps` prepares every path before executing any step, so adjacent screenshot steps receive identical paths even if the actual captures happen far apart. Later saves overwrite earlier evidence while the journal points multiple steps to the same final image. Concurrent visual requests can collide for the same reason.

**Reproduced:** a dry-run batch of 100 screenshot steps produced 100 paths but only 2 distinct names. No scheduling hypothesis is needed to establish the collision.

**Fix:** allocate a unique filename per capture using a GUID or another collision-safe identity; keep the timestamp for readability. Verify uniqueness within a batch and under concurrency, then verify each journal image retains its own content.

### F07 [P2] visual grounding does not retain the captured window identity

**Evidence:** `src/Winsight.Mcp/Tools/FindElementVisuallyTool.cs:95-105`, `:127-128`; `WindowGeometry.cs:48`; `WindowCapture.cs:35`.

The capture resolves the current topmost matching window, awaits inference, then independently resolves a window again for coordinate enrichment and again for clicking. The captured HWND is not retained. If a dialog opens/closes or the matching window order changes during inference, coordinates from window A are interpreted relative to window B. Passing a non-unique title fragment does not remove the problem.

**Verification:** static async call-chain inspection; no timed window-switch reproduction was performed. This is separate from F04: it can select the wrong window within the same process even without another application covering it.

**Fix:** return HWND and geometry with capture metadata, bind the grounded result to that identity, and revalidate it before action. On disappearance or incompatible geometry change, require a fresh capture rather than resolving a replacement window.

### F08 [P2] a rejected visual click is reported as top-level success

**Evidence:** `src/Winsight.Mcp/Tools/FindElementVisuallyTool.cs:127-131`.

The result of `ClickPoint` is always wrapped in `OperationResult.OkWith`. A caller using the normal top-level success contract proceeds even when the requested action failed. The nested click result is available, but other macro wrappers already propagate failure through their outer result.

**Reproduced:** a stub grounder returned confidence 1 and coordinates outside the sample bounds. No mouse input was sent. Output: `VISION_OUTER_SUCCESS=True`, `VISION_CLICK_SUCCESS=False`.

**Fix:** preserve grounding details while returning an outer failure when `click.Success` is false. Add a wrapper-level regression rather than testing only confidence parsing.

### F09 [P2] unexecuted vision gates count as passed tests

**Evidence:** `tests/Winsight.Core.Tests/OnnxLocalGrounderIntegrationTests.cs:39-43`; `QwenImagePreprocessingParityTests.cs:38-42`; `tests/Winsight.E2E/VisionGroundingPrecisionTests.cs:56-59`.

The three facts return early when their model/image/reference variables are absent. A return is a passing test, not a skipped test. All three were counted green in this audit without exercising their assertions; the checked-in CI workflow does not provision their required fixtures either.

**Fix:** use explicit runner-supported skips and make the provisioned vision suite a separately identifiable gate. Release evidence should distinguish unavailable inference tests from exercised tests. This finding does not claim that the model is inaccurate.

## Action plan

1. Close the process-boundary bypass first (F01), with an independent denied-target unchanged oracle.
2. Make forced termination explicitly requested (F02), enforce dry-run for baselines (F03), and prevent physical input landing on another process (F04).
3. Preserve action outcomes when tracing fails (F05), and allocate unique capture identities (F06).
4. Bind visual results to the captured HWND (F07) and propagate click failure (F08).
5. Correct the vision test accounting and document the actual exercised gates (F09).
6. Re-run the existing suite plus these counter-checks after scoped fixes; real model validation requires provisioned fixtures.

## Deliberately not flagged

- No network authentication, CORS, CSRF, or web security-header defect was invented for a local stdio server.
- The advertised cloud backend is explicit; unknown backend values and the ONNX backend fail without silently switching to cloud.
- Initial baseline creation is documented and distinguishable by its verdict. F03 concerns mutation despite dry-run, not ordinary first-run behavior.
- Core's use of Windows interop/UIA is the purpose of this Windows SDK, not an architectural layering violation.
- Obvious-type `var` is explicitly allowed by the repository's `.editorconfig`; no global style replacement is proposed.
- Existing DLL locks were verified live and worked around without terminating user sessions. They are not counted as a compiler regression.
- Model precision, memory leaks, complete accessibility compliance, and remote CI status are not inferred from passing unit tests.
